모듈 베이스와 시퀀스 (층 2)

2026-10-09 개정이전: 구현 가이드 01 운전 상태 모델다음: 03 챔버와 LoadLock

클래스 모습, 멤버와 시그니처, 쓰인 C# 개념은 AI가 정했어요. 메서드 본문은 현성님이 작성해요. 본문 예시는 ModuleBase.Abort()와 파생 모듈의 시퀀스 세 개예요. 시퀀스는 앞으로 LoadLock을 쓸 때 그대로 따라 할 모양이라 전부 보여 줘요.

이 가이드는 TcHit을 참고만 했어요. 도메인에서 필요한 규칙(에러 래칭, Abort 전파, Manual 탈출구)은 남기고, PLC 제약에서 나온 방식(int 에러 코드, seqNo CASE, Exec/Busy/Done 칸, 한 줄로 이어진 인터페이스 상속)은 C# 방식으로 바꿨어요.

1이번에 정한 것

층 1 · 완료

OperationStateMachine

상태, 명령 수락, 완료 조건을 보고 자동 전이, 이력, 타임아웃.

층 2 · 이번

SequenceRunner

스텝을 하나씩 진행하는 실행기. 스텝 타임아웃, 일시정지 경계, 취소.

층 2 · 이번

ModuleBase

상태머신과 실행기 세 개를 들고, 명령에 맞춰 시퀀스를 시작·취소. 하위 에러 수집, Abort/ClearFault 전파.

  1. 에러는 bool Error + int ErrorID 대신 Fault? Fault 하나로 표현해요. Fault는 출처, 코드(enum), 메시지를 담은 record예요. 해제 메서드는 ClearFault()예요. (3절)
  2. 하위 계약은 서로 독립된 작은 인터페이스 셋이에요. IFaultSource, IStandStill, IAbortable. 클래스가 필요한 것만 골라 구현해요. (4절)
  3. 시퀀스는 seqNo CASE 대신 C# 이터레이터(yield return)로 써요. 한 번에 하나씩 꺼내지는 각 스텝은 Step 객체로, 이름, 동작, 완료 조건, 타임아웃을 데이터로 가져요. (5~7절)
  4. Exec/Busy/Done 같은 단계 개념은 없애요. 시작은 명령이 수락될 때, 완료는 시퀀스가 끝까지 갔을 때, 중단은 실행기를 취소할 때예요.
  5. 모듈은 상태머신을 상속하지 않고 필드로 가져요. (8절)
  6. Fault가 생기면 베이스가 자동으로 Abort해요. Aborting 시퀀스는 스텝이 실패해도 다음 스텝으로 계속 가요. (9절)
  7. 멈춘 상태 네 개(Aborted, Homed, Paused, Stopped)는 모두 "하위 전원 StandStill"을 완료 조건으로 가져요.
  8. ModeSelector의 Maint/Auto 변경 조건에 모듈 StandStill을 추가해요. Manual에는 추가하지 않아요. (11절)

사양서 6~7주차의 시퀀스 엔진 항목 중 정의 구조, 실행, 일시정지/재개/중단, 구조화된 실패가 이번에 앞당겨 들어와요. 사양서의 "시퀀스를 데이터로 표현"은 스크립트 언어를 만들라는 뜻으로 받지 않아요. 순서와 분기는 C# 코드로 쓰고, 각 스텝의 이름·타임아웃은 데이터로 남기는 방식으로 해석했어요. 공정 값(압력, 시간)은 나중에 레시피에서 받아요.

3Fault — 에러를 값 하나로

public sealed record Fault(string Source, Enum Code, string Message);

지금 장치들은 bool Error와 int ErrorID 두 개로 에러를 알려요. PLC에서는 enum을 UDINT로 실어 나를 수밖에 없어서 생긴 방식이에요. C#에서 이걸 그대로 쓰면 두 가지 문제가 생겨요. 밸브의 1(OpenTimeout)과 펌프의 1(RunTimeout)이 같은 숫자라, 모듈이 하위 에러를 모으는 순간 무슨 뜻인지 알 수 없어요. 누가 냈는지도 안 따라와요.

Fault는 그 세 가지(누가, 무엇을, 사람이 읽을 설명)를 하나로 묶어요. 에러가 없으면 null이에요. 그래서 Error와 ErrorID가 따로 어긋날 일도 없어요.

예전이제
valve.Errorvalve.Fault is not null
valve.ErrorID == (int)ValveErrorCode.OpenTimeoutvalve.Fault?.Code is ValveFault.OpenTimeout
Error = true; ErrorID = ...;Fault = new Fault(Name, ValveFault.OpenTimeout, "Open 응답 없음");
Reset()ClearFault()

에러 enum은 이름을 XxxFault로 맞춰요. ValveFault, PumpFault, AnalogSensorFault, OperationFault. "에러 없음"은 null이 맡으니까 enum의 None/NoError 멤버는 지워요.

"최초 원인 하나만 남긴다"는 기존 규칙은 그대로예요. 이미 Fault가 있으면 새로 덮지 않아요. 장치는 지금도 에러 중에 Scan이 return하니까 자연스럽게 지켜져요.

C# 개념: Enum 타입으로 받기

Enum(대문자)은 모든 enum의 공통 부모 타입이에요. Enum Code에는 ValveFault든 PumpFault든 어떤 enum 값이든 들어가고, 원래 타입을 기억해요. 그래서 fault.Code is ValveFault.OpenTimeout처럼 타입과 값을 함께 확인할 수 있고, fault.Code.ToString()은 "OpenTimeout"이라는 이름을 돌려줘요. 로그나 화면에 숫자 대신 이름이 나와요.

C# 개념: ??= 연산자

a ??= b;는 "a가 null일 때만 b를 넣는다"예요. 최초 원인 유지 규칙이 연산자 하나로 표현돼요. 모듈에서 쓰게 돼요.

Fault ??= new Fault(Name, code, message);   // 이미 있으면 그대로
PLC로 치면

IF NOT SeqError THEN SeqError := TRUE; SeqErrorID := id; StateMsg := ...; END_IF 세 변수를 Fault 하나에 담고, IF 문을 ??=로 줄인 거예요.

발생 시각은 넣지 않았어요. 장치가 시각을 찍으려면 clock을 필드로 들어야 하는데, 그건 "파츠는 clock을 타이머에만 넘긴다" 규칙과 부딪혀요. 나중에 알람 계층이 Fault를 처음 본 스캔에 시각을 찍으면 한 스캔 안의 오차로 충분해요.

4기능 인터페이스 셋

public interface IFaultSource
{
    Fault? Fault { get; }        // null = 정상
    void ClearFault();           // 래치 해제
}

public interface IStandStill
{
    bool StandStill { get; }     // 진행 중인 명령 동작이 없다
}

public interface IAbortable
{
    bool Abort();                // 즉시 정지. 항상 수락
}

IFaultSource에 Name이 없는 건 의도예요. 이름은 장치의 신원이지 고장의 속성이 아니에요. 고장을 받는 쪽에 필요한 "누가 냈나"는 Fault.Source에 이미 들어 있어요. 이름은 IValve, IPump, IAnalogSensor처럼 장치 인터페이스가 각자 가져요. 나중에 이름만 공통으로 모아 볼 일이 생기면 그때 이름 전용 인터페이스를 따로 둬요.

셋은 서로 상속하지 않아요. 클래스가 필요한 것만 쉼표로 이어 붙여요. 인터페이스도 여러 개를 상속할 수 있어서 interface IValve : IFaultSource, IStandStill처럼 써요.

타입구현하는 기능
IAnalogSensorIFaultSource
IValve, IPumpIFaultSource, IStandStill
OperationStateMachineIFaultSource
ModuleBaseIFaultSource, IStandStill, IAbortable
로봇, 유닛 (나중)IFaultSource, IStandStill, IAbortable

TcHit은 ErrorReset → StandStill → Abortable을 한 줄로 상속했어요. 등록 배열의 타입을 하나로 맞춰야 했기 때문이에요. C#은 목록 하나에 담아 두고 is나 OfType으로 기능을 골라낼 수 있으니 그럴 필요가 없어요. 독립시켜 두면 "Abort는 되는데 정지 보고는 없는" 것도, "에러 보고만 하는" 센서도 억지 없이 표현돼요.

장치 인터페이스는 이렇게 줄어요

public interface IValve : IFaultSource, IStandStill
{
    string Name { get; }
    Permissive OpenPermissive { get; }
    Permissive ClosePermissive { get; }
    ValveState State { get; }

    bool Open();
    bool Close();
}

Error, ErrorID, Reset 세 줄은 지우고 Name은 남겨요. 명령은 Fault가 있으면 거부해요. if (!OpenPermissive.IsAllowed || Fault is not null) return false;

StandStill의 정의

밸브는 State is not (ValveState.Opening or ValveState.Closing), 펌프는 State is not (PumpState.Starting or PumpState.Stopping)이에요. 이름은 PLCopen에서 온 모션 제어 용어인데, 언어와 상관없는 업계 용어라 그대로 써요.

에러 뒤의 Unknown도 StandStill로 쳐요. 타임아웃 난 밸브를 "동작 중"으로 보면 Aborting 완료 조건(하위 전원 StandStill)이 영원히 안 채워져서 Aborting에 갇혀요. 고장 자체는 Fault로 따로 올라가고, Fault가 있는 동안 Home이 거부되니 위험하지 않아요.

5시퀀스 — 큰 그림

이번 가이드에서 가장 크게 바뀐 부분이에요. 먼저 전체 그림을 TwinCAT 방식과 나란히 놓고 볼게요.

TwinCAT에서는

Homing 메서드가 매 스캔 불려요. 메서드 안에서 CASE seqNo로 지금 어느 칸인지 보고, 그 칸의 일을 하고, 조건이 되면 seqNo를 다음 번호로 바꿔요. 스캔이 끝나도 seqNo는 FB의 VAR라 남아 있으니 다음 스캔에 이어서 진행돼요. "어디까지 했는지"를 개발자가 seqNo로 직접 관리하는 거예요.

C# 이터레이터에서는

같은 일을 위에서 아래로 그냥 써요.

protected override IEnumerable<Step> Homing()
{
    yield return new Step("게이트 닫기", Action: gate.Close, Until: () => gate.State == ValveState.Closed);
    yield return new Step("펌프 기동", Action: pump.Run, Until: () => pump.State == PumpState.Running);
}

yield return은 "이 스텝을 내보내고 여기서 멈춘다"는 뜻이에요. 실행기가 다음 스텝을 달라고 하면 멈췄던 자리 바로 다음 줄부터 이어서 실행돼요. 어디까지 했는지는 컴파일러가 기억해요. 실제로 C# 컴파일러는 이 메서드를 숨은 상태 번호와 switch를 가진 클래스로 바꿔요. seqNo CASE를 컴파일러가 대신 만들어 주는 셈이에요.

TwinCATC# 이터레이터
seqNo 변수와 CASE컴파일러가 만든 숨은 상태 (지금 멈춰 있는 yield 위치)
seqNo := 20; 다음 칸으로다음 yield return
IF 이미 닫힘 THEN seqNo := 30; 건너뛰기그냥 if 문
seqNo := 0; 처음으로 반복while 문
seqNo := 1000; + 완료 조건 등록메서드가 끝나면 완료 (실행기가 알아서 판정)
Exec 칸의 초기화첫 yield return 앞에 쓴 코드
ErrExec 칸에서 Abort실행기 취소 (베이스가 함)
AddLog(seqNo, '...')Step.Name (지금 스텝 이름이 항상 보임)
스텝별 TON 타임아웃Step.Timeout
지역 변수는 VAR에메서드 지역 변수가 yield 사이에서도 유지됨

스캔 구조는 그대로예요. 스캔 스레드가 매 스캔 실행기를 부르고, 실행기는 지금 스텝의 완료 조건을 보고, 끝났으면 다음 스캔에 다음 스텝을 꺼내요. 블로킹은 어디에도 없어요.

왜 async/await가 아니고 이터레이터인가

C#에서 "순서대로 쓰고 중간에 기다린다"면 보통 async/await를 떠올려요. 그런데 await는 기다림이 끝나면 스레드 풀의 아무 스레드에서나 이어서 실행돼요. 스캔 스레드 밖에서 장치 상태를 건드리게 되니 ADR 0003의 스캔 구조와 맞지 않아요. 이터레이터는 누군가 다음을 달라고 할 때만, 그 호출한 스레드에서 한 칸 진행해요. 실행기를 스캔에서 부르면 시퀀스도 정확히 스캔 안에서만 움직여요.

C# 개념: 이터레이터는 게으르다

Homing()을 호출해도 본문은 한 줄도 실행되지 않아요. 호출은 "진행할 준비가 된 객체"만 돌려줘요. 본문은 그 객체에 첫 번째 다음(MoveNext)을 요청할 때 첫 yield return까지 실행돼요. 그래서 명령 메서드에서 Homing()을 불러 실행기에 넘겨도 안전해요. 실제 동작은 다음 스캔에 시작돼요.

IEnumerator<Step> e = Homing().GetEnumerator();   // 아직 아무것도 안 함
e.MoveNext();     // 첫 yield return까지 실행. true = 스텝 하나 나옴
Step s = e.Current;
e.MoveNext();     // 다음 yield return까지. 메서드가 끝났으면 false

6Step — 스텝 하나

public sealed record Step(
    string Name,
    Func<bool>? Action = null,      // 스텝 시작 시 한 번. false = 명령 거부
    Func<bool>? Until = null,       // 완료 조건. 매 스캔 확인. null이면 바로 완료
    TimeSpan? Timeout = null);      // 공정 타임아웃. null이면 감시 안 함

public enum SequenceFault { ActionRejected, StepTimeout }

스텝은 세 가지 모양으로 쓰여요.

new Step("게이트 닫기", Action: gate.Close, Until: () => gate.State == ValveState.Closed)   // 명령 + 도달 대기
new Step("진공 도달", Until: () => gauge.Value <= 0.1, Timeout: TimeSpan.FromMinutes(3))    // 기다리기만
new Step("벤트 밸브 열기", Action: vent.Open)                                                // 명령만

타임아웃의 주인이 여기서 정리돼요. 밸브가 명령에 응답하지 않는 건 밸브가 스스로 타임아웃을 내요(장치 응답 타임아웃). 압력이 3분 안에 안 떨어지는 건 장치 고장이 아니라 공정 문제라 스텝의 Timeout이 맡아요(공정 타임아웃). 전에 정한 "장치 응답 타임아웃은 장치, 공정 타임아웃은 시퀀스/레시피"의 시퀀스 쪽 자리가 이제 생긴 거예요.

C# 개념: Func<bool>과 메서드 그룹

Func<bool>은 "인자 없이 bool을 돌려주는 함수"를 담는 타입이에요. Permissive의 조건이 이미 이 타입이에요. Action: gate.Close처럼 괄호 없이 메서드 이름만 쓰면 "그 메서드 자체"가 넘어가요(메서드 그룹). 지금 호출하는 게 아니라 나중에 실행기가 부를 함수를 넘기는 거예요. gate.Close()로 괄호를 붙이면 그 자리에서 바로 실행되니 주의하세요.

C# 개념: 이름 붙인 인자

Action:, Until:, Timeout:처럼 매개변수 이름을 붙여 넘길 수 있어요. 기본값이 있는 매개변수는 건너뛸 수 있어요. 스텝을 읽을 때 무엇이 동작이고 무엇이 조건인지 바로 보여요.

7SequenceRunner — 실행기

public sealed class SequenceRunner
{
    #region Fields
    private readonly string owner;              // Fault.Source에 넣을 이름 (모듈 이름)
    private readonly OnDelayTimer timer;        // 지금 스텝의 경과 시간
    private IEnumerator<Step>? steps;
    #endregion

    #region Properties
    public Step? Current { get; private set; }            // 진행 중인 스텝. null = 스텝과 스텝 사이
    public bool IsActive => steps is not null;            // 시작했고 아직 안 끝남
    public bool IsCompleted { get; private set; }         // 끝까지 갔음
    public bool AtBoundary => Current is null;
    #endregion

    #region Constructor
    public SequenceRunner(string owner, IClock clock)
    #endregion

    #region Methods
    public void Start(IEnumerable<Step> sequence)
    public void Cancel()
    public Fault? Advance(bool hold)                      // 스캔마다 한 번. 실패하면 Fault 반환
    #endregion
}

Start, Cancel (직접 작성)

Start는 먼저 Cancel()로 하던 걸 버리고, steps = sequence.GetEnumerator(), IsCompleted = false로 둬요.

Cancel은 steps?.Dispose() 후 steps = null, Current = null, IsCompleted = false, timer.Stop()이에요. Dispose를 부르면 이터레이터 안의 finally 블록이 실행되고 정리돼요. ?.는 "null이 아니면 호출"이에요.

Advance가 할 일 (직접 작성)

  1. steps가 null이면 null을 반환하고 끝.
  2. Current가 null이면 (스텝 사이)
    • hold면 아무것도 하지 않고 null 반환. 일시정지는 여기서 걸려요.
    • steps.MoveNext()가 false면 시퀀스 끝. IsCompleted = true, steps.Dispose(), steps = null, null 반환.
    • 아니면 Current = steps.Current, timer.Tick(). Current.Action이 있으면 부르고, false면 실패(ActionRejected).
  3. 완료 확인. Current.Until이 null이거나 true면 Current = null, timer.Stop(), null 반환. 다음 스텝은 다음 스캔에 꺼내요.
  4. 타임아웃 확인. Current.Timeout이 있고 timer.ElapsedTime()이 그 이상이면 실패(StepTimeout).
  5. null 반환 (진행 중).

실패 처리는 공통이에요. new Fault(owner, 코드, $"{Current.Name}: 설명")을 만들고, Current = null, timer.Stop() 후 그 Fault를 반환해요. 실패한 스텝은 끝난 것으로 쳐요. 다음에 무엇을 할지(Abort할지, 다음 스텝으로 갈지)는 실행기가 아니라 모듈이 정해요.

$"{Current.Name}: 설명"은 문자열 보간이에요. 중괄호 안의 값이 문자열에 끼워져요.

한 스캔에 스텝 하나

3번에서 스텝이 끝나도 같은 스캔에 다음 스텝을 꺼내지 않아요. 이 규칙이 없으면 while (true) { yield return new Step("x"); } 같은 실수 하나로 스캔 스레드가 무한 루프에 빠져요. 한 스텝이 최소 한 스캔을 차지하니까 그런 실수가 나도 시퀀스가 느리게 돌 뿐 스캔은 멈추지 않아요.

PLC로 치면

CASE의 한 칸이 최소 한 스캔인 것과 같아요. 2번에서 동작과 3번 완료 확인은 같은 스캔에 일어나요. 이미 닫혀 있는 밸브에 Close를 걸면 Close가 true만 돌려주고 State가 Closed라서 그 스캔에 바로 끝나요. TcHit 샘플의 "이미 대기 자세면 생략"이 따로 코드를 쓰지 않아도 돼요.

상태머신을 상속하지 않고 필드로 갖는 이유

TcHit의 FB_Module은 EXTENDS FB_StateMachine이었어요. C#에서 class ModuleBase : OperationStateMachine로 가면 상태머신의 public 멤버가 전부 모듈의 public 멤버가 돼요. 밖에서 완료 조건을 넣거나, 하위 전파 없는 Abort를 부를 길이 열려요. Abort에 전파를 끼우려면 virtual을 열어야 하는데, 그러면 층 1의 수락 규칙도 파생 클래스가 바꿀 수 있게 돼요. 그리고 C# 클래스는 부모를 하나만 가질 수 있어요.

필드로 가지면 밖에서 보이는 건 ModuleBase가 정한 것뿐이고, 층 1은 지금 모습과 테스트 그대로 유효해요. 상태머신을 protected로 둔 건 파생 모듈이 생성자에서 조건(예: RunningCondition, RunPermissive)을 등록해야 해서예요.

규칙

파생 모듈은 StateMachine.Abort() 같은 상태머신 명령을 직접 부르지 않아요. 시퀀스 시작과 하위 전파가 빠져요. 상태머신은 조건 등록용으로만 써요.

실행기를 세 개 두는 이유

한 순간에 도는 시퀀스는 하나뿐이니 실행기 하나로도 돼요. 하지만 그러면 완료 조건이 "지금 실행기가 Homing 것이고 끝났는가"처럼 종류까지 따져야 해요. 세 개를 두면 HomedCondition은 homingRunner.IsCompleted 한 줄이에요. 객체 두 개 더 만드는 비용으로 조건이 단순해져요.

C# 개념: abstract, protected, override

abstract class는 new 할 수 없고 상속해서만 써요. protected abstract IEnumerable<Step> Homing();은 본문 없는 메서드로, 파생 클래스가 protected override로 반드시 채워야 해요. 빠지면 컴파일 에러예요. 할 일이 없는 시퀀스는 yield break; 한 줄로 채워요(바로 끝나는 시퀀스).

PLC로 치면

FUNCTION_BLOCK ABSTRACT, METHOD PROTECTED ABSTRACT와 같아요. 차이는 TcHit의 Homing은 매 스캔 불리는 메서드였고, 여기 Homing은 Home 명령이 수락될 때 한 번 불려서 "스텝들을 내놓는 객체"를 돌려준다는 점이에요. 매 스캔 진행시키는 건 실행기예요.

C# 개념: LINQ OfType / All, ?? 연산자

components.OfType<IStandStill>()는 목록에서 IStandStill인 것만 골라내고, .All(...)은 전부 조건을 만족하는지 봐요. 비어 있으면 true예요. TcHit의 __QUERYINTERFACE + FOR 루프 AND를 한 줄로 쓴 거예요.

a ?? b ?? c는 "null이 아닌 첫 번째"예요. CurrentStep은 세 실행기 중 진행 중인 스텝이 있는 것을 보여 줘요.

명령은 시퀀스를 시작한다

시퀀스는 스캔에서 상태를 보고 시작하지 않고, 명령이 수락되는 그 자리에서 시작해요. 이유가 있어요. Home 명령이 스캔과 스캔 사이에 들어오면, 다음 스캔에서는 층 1이 모듈보다 먼저 돌아요(아래). 그때 homingRunner.IsCompleted가 지난번 Home의 값(true)으로 남아 있으면 층 1이 그 스캔에 바로 Homed로 넘겨 버려요. 명령 안에서 Start를 부르면 IsCompleted가 false로 먼저 바뀌니 이런 일이 없어요. Start는 이터레이터를 만들기만 하고 본문은 실행하지 않으니 명령 안에서 불러도 가벼워요.

명령수락되면
AbortHoming·Running 실행기 Cancel, abortingRunner.Start(Aborting()), 하위 IAbortable 전파
HomehomingRunner.Start(Homing())
RunPaused에서 온 재개면 아무것도 안 함(멈춘 자리부터 이어감). 아니면 runningRunner.Start(Running())
SemiAutorunningRunner.Start(Running())
Pause, Stop상태머신에 넘기기만 해요. 진행 방식은 스캔이 상태를 보고 바꿔요

재개인지는 StateMachine.Run()이 true를 반환한 직후 StateMachine.Resumed로 알 수 있어요. 재개할 때 처음부터 다시 시작하지 않으니, TcHit처럼 "Exec 칸에서 P_Resumed로 초기화를 막는" 코드가 파생 모듈에서 사라져요.

예시: Abort() 전체

public bool Abort()
{
    if (State == OperationState.Aborting) return true;   // 재진입: 다시 시작하지도, 전파하지도 않는다

    StateMachine.Abort();
    homingRunner.Cancel();
    runningRunner.Cancel();
    abortingRunner.Start(Aborting());

    foreach (IFaultSource component in components)
    {
        if (component is IAbortable abortable)
            abortable.Abort();
    }
    return true;
}

하위 Abort는 수락 즉시 나가요. Aborting 시퀀스의 첫 스텝은 다음 스캔에 시작되니, 하위는 그보다 먼저 멈춰요. 정지 전에 판정할 게 있는 하위는 AddComponent로 등록하지 말고 Aborting 시퀀스의 스텝에서 직접 불러요.

component is IAbortable abortable는 "component가 IAbortable이면 그 타입으로 abortable에 담고 true"예요.

PLC로 치면

IF __QUERYINTERFACE(iComponents[i], iAbortable) THEN iAbortable.Abort();와 같아요.

Home, Run, SemiAuto는 같은 모양이에요. 상태머신 명령이 false면 바로 false를 반환하고, true면 위 표대로 시작한 뒤 true를 반환해요. 이 명령들은 virtual로 열지 않아요. 수락 조건을 더하고 싶으면 override가 아니라 Permissive를 써요.

ClearFault, RaiseFault, AddComponent (직접 작성)

ClearFault()는 Fault = null, StateMachine.ClearFault(), 하위 전원 ClearFault()예요. 하위 고장 원인이 그대로면 다음 스캔에 다시 Fault가 잡혀요. 그게 맞는 동작이에요.

RaiseFault(Enum code, string message)는 Fault ??= new Fault(Name, code, message); 한 줄이에요. 파생 모듈이 시퀀스 중에 공정 판단으로 에러를 낼 때 써요.

AddComponent는 목록에 이미 있으면 무시하고 없으면 추가해요. protected라서 파생 모듈 생성자에서만 부를 수 있어요. "하위 등록은 생성 시 한 번"을 접근 제한자로 지키는 거예요.

Scan이 할 일 (직접 작성)

  1. 하위 Fault 수집. 모듈 Fault가 아직 없으면 상태머신 Fault, 그다음 하위 중 첫 Fault를 가져와요. Fault ??= StateMachine.Fault ?? components.Select(c => c.Fault).FirstOrDefault(f => f is not null);
  2. 지금 상태에 맞는 실행기를 한 번 진행해요. switch 식으로 고르면 깔끔해요. 
    Fault? failure = State switch
{
    OperationState.Aborting => abortingRunner.Advance(hold: false),
    OperationState.Homing => homingRunner.Advance(hold: false),
    OperationState.Idle or OperationState.Running or OperationState.Stopping or OperationState.SemiAuto
        => runningRunner.Advance(hold: false),
    OperationState.Pausing or OperationState.Paused => runningRunner.Advance(hold: true),
    _ => null
};
  3. Fault ??= failure;
  4. 자동 Abort. Fault가 있고 상태가 Homing, Idle, Running, Pausing, Stopping, SemiAuto 중 하나면 Abort().
주의: ??= 오른쪽은 왼쪽이 null일 때만 실행된다

Fault ??= abortingRunner.Advance(false);처럼 한 줄로 쓰면 안 돼요. 모듈에 이미 Fault가 있으면 오른쪽 자체가 실행되지 않아서 Advance가 불리지 않아요. 에러로 Abort된 모듈의 Aborting 시퀀스가 영원히 진행되지 않게 돼요. 2번처럼 Advance 결과를 변수에 먼저 받고, 3번에서 래칭해요.

1번을 2번보다 먼저 하는 이유는 시간 순서예요. 하위 장치 Scan은 모듈 Scan보다 먼저 돌아서, 같은 스캔에 둘 다 생겼다면 하위 쪽이 먼저 생긴 거예요. 밸브가 응답하지 않아 스텝이 타임아웃 났다면 원인으로 남아야 하는 건 밸브 Fault예요.

Pausing에서 hold: true를 넘기면 진행 중이던 스텝은 끝까지 가고, 다음 스텝을 꺼내지 않아요. 그 순간 AtBoundary가 true가 되어 층 1이 Paused로 넘겨요. Run으로 재개하면 hold가 풀려 다음 스텝부터 이어가요.

Aborting 중에는 스텝이 실패해도 실행기가 그 스텝을 끝난 것으로 치고 다음 스캔에 다음 스텝으로 가요. Fault만 남아요. Abort는 에러에 대한 대응 그 자체라서, 정지 동작 하나가 실패했다고 나머지 정지 동작을 건너뛰면 안 되기 때문이에요.

자동 Abort를 베이스가 하는 이유

TcHit은 파생 모듈의 ErrExec 칸에 Abort를 직접 쓰게 했어요. 장비(머신)가 모듈에 Abort를 전파하는 구조가 위에 있었기 때문이에요. 우리 모듈은 단독으로 돌고, 위에서 Abort를 걸어 줄 객체가 없어요. 파생 모듈마다 쓰게 하면 하나만 빠뜨려도 에러 난 채로 시퀀스가 계속 돌아요. 그래서 "Fault = 정지"를 베이스에 고정해요.

Homed, Paused, Stopped, Aborted에서는 Abort하지 않아요. 시퀀스가 돌고 있지 않고, Fault 중에는 Home·Run·SemiAuto가 거부되니 그걸로 충분해요. Homed에서 Aborted로 떨어뜨리면 Home을 다시 해야 해서 손해예요.

StandStill

public bool StandStill =>
    (State is OperationState.Aborted or OperationState.Homed or OperationState.Paused or OperationState.Stopped)
    && ComponentsStandStill;

스캔 순서와 진행 예

스캔 사이클은 등록 순서대로 불러요. 장치는 모듈 생성자의 인자라 먼저 만들어지고, 상태머신은 베이스 생성자 안에서, 모듈 Scan은 베이스 생성자 마지막에 등록돼요.

장치 Scan→상태머신 Scan→모듈 Scan

밸브 하나를 가진 모듈에 Home을 걸면 이렇게 가요(밸브 동작 시간 100ms, 스캔 10ms).

스캔상태머신 Scan모듈 Scan
명령Home() 수락 → 상태 Homing, homingRunner.Start (IsCompleted false)
1HomedCondition 미충족 → Homing 유지MoveNext → 스텝 "밸브 닫기", Close() → 밸브 Closing, Until 거짓
2~10미충족Until 거짓 (밸브 Closing)
11미충족밸브 Closed → Until 참 → Current null
12미충족 (아직 IsCompleted 아님)MoveNext false → IsCompleted true
13IsCompleted, 밸브 StandStill → Homed상태 Homed라 진행할 실행기 없음

층 1이 모듈 결과를 한 스캔 늦게 보는 건 ADR 0005에 적어 둔 그대로예요. 10ms 스캔에서 문제 되는 크기가 아니에요.

C# 개념: 생성자 실행 순서

: base(...)는 부모 생성자를 먼저 실행한다는 뜻이에요. 부모 생성자가 끝까지 돈 다음에 파생 생성자 본문이 실행돼요.

주의: 베이스의 "마지막 줄"은 객체의 마지막 줄이 아니다

ModuleBase 생성자 마지막 줄에서 Scan을 등록해도, 그 뒤에 파생 생성자 본문(장치 필드 대입, 조건 등록)이 남아 있어요. 다른 스레드에서 스캔이 이미 돌고 있다면 파생 필드가 null인 채로 Scan이 불릴 수 있어요. 테스트에서는 문제없어요. FakeScanCycle은 RunScans를 부를 때만 도는데 그건 조립이 끝난 뒤니까요. 실행용 스캔 사이클(Infrastructure)을 만들 때 "조립이 끝난 뒤 Start()로 시작한다"를 요구 사항으로 넣어야 해요. 그게 실제 안전장치예요.

10파생 모듈은 이렇게 쓴다 — SampleModule

테스트용 모듈이에요. 밸브 하나를 갖고, Home하면 밸브를 닫고, Run하면 일감이 들어올 때마다 밸브를 열었다 닫아요. LoadLock도 같은 모양으로 쓰게 돼요. 테스트 프로젝트에 둬요.

public class SampleModule : ModuleBase
{
    #region Fields
    private readonly IValve valve;
    private readonly TimeSpan? openTimeout;
    #endregion

    #region Properties
    public bool HasWork { get; set; }               // 테스트가 일감 유무를 넣는다
    public int CycleCount { get; private set; }     // 끝낸 사이클 수
    #endregion

    #region Constructor
    public SampleModule(string name, IValve valve, ModeSelector mode, TransitionTimeouts timeouts,
                        IClock clock, IScanCycle scanCycle, TimeSpan? openTimeout = null)
        : base(name, mode, timeouts, clock, scanCycle)
    {
        this.valve = valve;
        this.openTimeout = openTimeout;
        AddComponent(valve);

        StateMachine.RunningCondition.AddCondition(() => HasWork, "일감 없음");
    }
    #endregion

    #region Methods
    public void AddForTest(IFaultSource component) => AddComponent(component);
    public void RaiseForTest(Enum code) => RaiseFault(code, "테스트");

    protected override IEnumerable<Step> Aborting()
    {
        yield break;      // 밸브는 출력 유지 장치라 정지할 게 없다
    }

    protected override IEnumerable<Step> Homing()
    {
        yield return new Step("밸브 닫기", Action: valve.Close, Until: () => valve.State == ValveState.Closed);
    }

    protected override IEnumerable<Step> Running()
    {
        while (!StopRequested)
        {
            yield return new Step("일감 대기", Until: () => HasWork || StopRequested);
            if (StopRequested) yield break;

            yield return new Step("밸브 열기", Action: valve.Open,
                                  Until: () => valve.State == ValveState.Opened, Timeout: openTimeout);
            yield return new Step("밸브 닫기", Action: valve.Close,
                                  Until: () => valve.State == ValveState.Closed);
            CycleCount++;
        }
    }
    #endregion
}

Running이 반복 구조인 걸 보세요. Run을 받으면 Stop 요청이 올 때까지 사이클을 돌아요. Stop(사이클 스톱)이 오면 지금 사이클을 끝까지 마치고 while 조건에서 빠져나가 시퀀스가 끝나요. 그러면 runningRunner.IsCompleted가 true가 되고 층 1이 Stopped로 넘겨요. 일감을 기다리는 스텝의 Until에 || StopRequested를 넣은 이유는, 일감이 없을 때 Stop이 오면 기다리던 스텝에서 바로 빠져나오게 하려는 거예요. 기다리는 스텝을 쓸 때마다 "여기서 Stop이 오면 어떻게 되나"를 생각해야 해요.

CycleCount++는 스텝이 아니라 그냥 코드예요. 두 yield 사이의 코드는 다음 스텝을 꺼낼 때 실행돼요. 상태 갱신이나 데이터 기록(웨이퍼 상태 변경 같은 것)은 이렇게 써요.

Exec 칸, seqNo, 완료 번호 등록, Resumed 확인, ErrExec에서 Abort 부르기가 전부 없어요. 파생 모듈은 "무엇을 어떤 순서로 하는가"만 써요.

이터레이터 안에서 하지 말 것

스텝 밖에서 장치 명령을 직접 부르지 마세요(valve.Open();만 단독으로). 거부돼도 아무도 모르고, 타임아웃도 안 걸려요. 명령은 항상 Step의 Action으로 넘겨요. 그리고 try/finally의 finally 안에 장치 명령을 넣지 마세요. Abort로 취소될 때 finally가 실행되는데, 정지 동작은 Aborting 시퀀스가 책임져야 해요.

FakeAbortable은 IFaultSource, IStandStill, IAbortable을 구현한 대역이에요. Name, Fault(set 가능), StandStill(set 가능, 기본 true), AbortCount, ClearCount를 두고, Abort()는 AbortCount를 올리고 true를 반환해요. ClearFault()는 ClearCount를 올리고 Fault를 null로 돌려요.

11ModeSelector — 고정 규칙에 StandStill 추가

// Fields에 추가
private readonly List<IStandStill> standStillMembers = new();

// Methods에 추가 — ModuleBase 생성자가 부른다. 이미 있으면 무시
internal void AttachStandStill(IStandStill member)

Change에서 Maint와 Auto로 바꿀 때만 standStillMembers.All(m => m.StandStill)을 고정 규칙에 AND해요.

Maint/Auto에 넣는 이유는, Aborted 상태에서도 Manual 조작으로 밸브가 움직이고 있을 수 있어서예요. 움직이는 중에 Auto로 넘어가면 Home 시퀀스가 그 밸브에 명령을 겹쳐 내요. Manual에 넣지 않는 이유는 데드락이에요. 장치가 안 멈춰서 Aborting에 갇혔을 때 Manual로 빠져서 손으로 정리하는 게 유일한 탈출구예요. 여기에 StandStill을 걸면 "안 멈춰서 갇혔는데 멈춰야 Manual로 갈 수 있다"가 돼요.

Attach와 이름을 나눈 건 두 목록의 뜻이 달라서예요. Attach는 상태 규칙(Aborted/Homed 등)의 대상, AttachStandStill은 정지 규칙의 대상이에요. 호출하는 줄만 봐도 어느 규칙에 들어가는지 보여요.

12테스트

기존 테스트 전환

FakeValveTest, OperatingStateMachineTest의 Error/ErrorID/Reset을 3절 표대로 바꿔요. 동작은 그대로라 전부 통과해야 해요. FakeValveTest에는 타임아웃 시 Fault.Source == "V1"을 확인하는 줄을 하나 추가해 주세요.

SequenceRunnerTest.cs

스캔 사이클 없이 FakeClock과 실행기만 만들고 Advance를 직접 불러요. 시간은 clock.Advance(...)로 밀어요. 시퀀스는 테스트 클래스 안에 private 이터레이터 메서드로 만들어 넘기면 돼요.

  1. Start만 하고 Advance하지 않으면 시퀀스 본문이 실행되지 않는다 (첫 yield 앞에서 카운터를 올려 확인)
  2. Until이 바로 참인 스텝 3개: Advance 3번에 스텝이 하나씩 끝나고, 4번째에 IsCompleted
  3. Until이 거짓인 동안 Current는 같은 스텝, 참이 되면 다음 Advance에 다음 스텝
  4. Action이 false를 반환하면 Fault.Code가 ActionRejected이고 Message에 스텝 이름이 있다
  5. Timeout을 넘기면 StepTimeout. Timeout이 null이면 아무리 기다려도 실패하지 않는다
  6. hold: true면 진행 중인 스텝은 끝까지 가고, 다음 스텝은 꺼내지 않는다 (AtBoundary true). hold를 풀면 이어서 진행
  7. Cancel하면 IsActive, IsCompleted 모두 false. 다시 Start하면 처음부터

ModuleBaseTest.cs

생성자에서 이 순서로 만들어요. 밸브를 먼저 만들어야 스캔 순서가 장치 → 상태머신 → 모듈이 돼요.

clock = new FakeClock();
scanCycle = new FakeScanCycle(clock, TimeSpan.FromMilliseconds(10));
valve = new FakeValve("V1", ValveState.Opened, TimeSpan.FromMilliseconds(100), TimeSpan.FromSeconds(1), clock, scanCycle);
mode = new ModeSelector(OperationMode.Maint);
module = new SampleModule("M1", valve, mode, new TransitionTimeouts(Aborting: TimeSpan.FromSeconds(1)), clock, scanCycle);

대부분의 테스트는 module.Abort() 후 RunScans(50ms)로 Aborted에서 시작하면 편해요. Run이 필요한 테스트는 new ModeSelector(OperationMode.Auto)로 만들어요. Auto에서도 Home은 수락돼요.

  1. Abort 후 1스캔에는 Aborting, 스캔 1번 더 돌리면 Aborted (빈 Aborting 시퀀스는 첫 스캔에 끝나고, 층 1은 다음 스캔에 그걸 본다)
  2. Aborted에서 밸브를 직접 Close하고 바로 Abort하면, 밸브가 Closing인 동안 Aborting 유지, 닫힌 뒤 Aborted
  3. FakeAbortable을 등록하고 Abort하면 AbortCount == 1. Aborting 중 Abort를 한 번 더 불러도 1
  4. Home → Homing 중 CurrentStep.Name == "밸브 닫기", StandStill false → Homed, StandStill true
  5. Homing 중 valve.RespondsToCommand = false → 1초 뒤 밸브 Fault → 모듈 Fault.Source == "V1", 스스로 Aborting → Aborted. Home 거부
  6. 5번 이어서 ClearFault → 밸브 Fault null, 모듈 Fault null, Home 수락
  7. FakeAbortable.Fault를 세우고 스캔을 한 번 돌린 뒤 RaiseForTest → 모듈 Fault는 FakeAbortable 것 그대로 (최초 원인 유지). 스캔 전에 부르면 모듈이 아직 하위 Fault를 못 본 상태라 RaiseForTest 쪽이 먼저가 돼요
  8. Homed 상태에서 FakeAbortable.Fault를 세우면 모듈 Fault는 생기지만 상태는 Homed 유지
  9. Auto: Run → Idle, CurrentStep "일감 대기" → HasWork = true → Running, 밸브가 열렸다 닫히며 CycleCount가 늘어난다. HasWork = false로 돌리면 사이클을 마친 뒤 "일감 대기"에서 Idle
  10. "밸브 열기" 진행 중에 Pause → 밸브가 열린 뒤 Paused, CurrentStep null. Run → "밸브 닫기"부터 이어감 (처음 "일감 대기"로 돌아가지 않음)
  11. 사이클 중 Stop → 그 사이클의 "밸브 닫기"까지 마치고 Stopped. HasWork가 false일 때 Stop하면 바로 Stopped
  12. openTimeout을 300ms로 만들고 사이클 중 valve.RespondsToCommand = false → 300ms 뒤 모듈 Fault.Code == SequenceFault.StepTimeout, Message에 "밸브 열기", 자동 Abort (밸브 타임아웃 1초보다 먼저)
  13. Aborted에서 밸브를 직접 Close(동작 중)하면 Auto 변경 거부, Manual 변경 수락. 밸브가 닫힌 뒤 Maint 변경 수락
  14. 모듈 Fault 중 Home은 거부되고 History는 늘지 않는다

테스트 이름은 검증 내용이 읽히게 지어 주세요. 예: Pause_DuringStep_FinishesStepThenPauses

13이번에 일부러 뺀 것

  • 스텝 실행 이력: 실행기가 스텝 시작·종료 시각과 결과를 목록에 남기면 돼요. Current와 Fault 메시지로 당분간 충분해서 미뤘어요. 사양서 6~7주차 항목이라 그때 넣어요.
  • SemiAuto 1스텝 진행: 실행기 hold를 "스텝 진행 버튼이 눌린 스캔만 false"로 주면 돼요. 구조는 이미 받쳐 줘요. 필요할 때 추가해요.
  • 장비 계층: 모듈 간 직접 핸드셰이크 방향이라 필요할 때 만들어요. ModuleBase가 IAbortable이니 그때 그대로 하위로 등록할 수 있어요.
  • 알람 계층: 여러 Fault를 목록으로 보여 주고, 발생 시각을 찍고, 이력을 DB에 남기는 것. Fault record가 그 재료가 돼요.
  • 경고 등급: 지금은 Fault = 정지 하나뿐이에요. 멈추지 않아도 되는 이상은 Fault가 아니라 경고로, 알람 등급을 정할 때 나눠요.
  • 명령 스레드와 스캔 스레드의 동시 접근: 명령이 실행기를 Start/Cancel하니 이 문제가 더 분명해졌어요. 실행용 스캔 사이클을 만들 때 lock 하나로 직렬화해요(ADR 0005 결정 그대로). Start() 시점 요구 사항도 그때 같이 반영해요.

다음 가이드 03에서는 챔버(진공 속성, 펌핑/벤팅)와 LoadLock 모듈을 다뤄요. 펌핑은 "러핑 밸브 열기 → 진공 도달(Timeout 있음) → 밸브 닫기" 같은 스텝 목록이 돼요.
