# 0002. 장치 에러는 장치가 래칭하고, 시간 기반 에러는 Scan()에서 검사한다

상태: 승인됨
날짜: 2026-09-27


## 배경

FakeValve 구현 중 에러 처리 구조가 정해지지 않아 작업이 멈췄다.
Error와 ErrorID를 계산식으로 표현하면 원인이 늘어날 때 확장이 불가능하다.
타임아웃처럼 시간이 지나야 알 수 있는 에러는 감지할 주체가 필요한데, C#에는 PLC의 스캔 주기가 없다.
이 결정이 없으면 가짜 장치, Load Lock 상태머신, 상태머신 테스트가 모두 막힌다.
관련 질문: 04 문서 Q9, Q10, Q11.


## 선택지

### 감지 시점 (Q9)

안 1: 장치마다 Update()를 두고 상위가 주기 호출. 경로가 하나라 단순하나 주기 주체가 필요하다.
안 2: Error를 읽을 때 검사. 가장 간단하나 아무도 읽지 않으면 에러가 뜨지 않는다.
안 3: 사건성 에러는 발생 지점에서, 시간 기반 에러만 Update()에서 검사.
안 4: 명령 시 타임아웃 감시 Task를 띄움. C#다운 방식이나 현재 FakeClock 구조와 맞지 않는다.

### 래칭 위치 (Q10)

안 1: 장치가 래칭하고 Reset()으로 해제.
안 2: 장치는 순간 상태만 알리고 알람 계층이 래칭.

### 에러 개수 (Q11)

안 1: 최초 발생 에러 하나만 유지.
안 2: 에러 목록 유지.


## 결정

감지 시점은 안 3(혼합), 래칭은 장치 + Reset(), 에러는 최초 원인 하나만 유지한다.

PLC 스캔 모델과 FB 래칭 방식을 그대로 옮겨 기존 경험과 맞추고, 테스트에서 FakeClock.Advance() 후 Update()를 호출해 시간을 결정적으로 통제할 수 있다.
안 2(읽을 때 검사)는 사양서 5.3의 이벤트/관찰 요구와 충돌해 버렸다.
감시 Task 방식은 FakeClock 재설계가 필요해 보류했다.
알람 계층 래칭은 아직 없는 계층에 의존하므로 버렸다.
에러 목록은 장치 수준에서 원인 종류가 적고 최초 원인이 가장 중요하므로 필요 없다고 판단했다.

추가: 시간에 따른 판단은 Update()가 유일한 지점이다. 가짜 장치의 상태 전이도 Update()에서 하고 getter는 필드만 반환한다.
전이를 getter에서, 타임아웃을 Update에서 판단하면 State와 Error가 어긋나기 때문이다.


## 결과

장치 인터페이스(IValve, IPump, IAnalogSensor)에 Reset()이 추가된다. 주기 판단 메서드는 인터페이스에 두지 않고 각 구현체의 private Scan()으로 둔다(ADR 0003).
가짜 장치와 상태머신 테스트를 대기 없이 결정적으로 작성할 수 있다.
Scan()을 주기 호출하는 구조는 ADR 0003에서 결정했다.
알람 계층은 장치 Error의 상승/하강을 보고 발생/해제 쌍을 기록한다.
모듈 단위에서 여러 장치 에러가 겹칠 때 목록 여부를 재검토한다.
명령 기반 비동기 감시로 바꾸고 싶어지면 FakeClock 설계와 함께 재검토한다.


## 변경 이력

2026-09-27: 본문의 Update()는 이후 Scan()으로 이름이 바뀌었고 private으로 숨겼다. 호출 구조는 ADR 0003 참조.
