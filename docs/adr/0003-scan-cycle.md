# 0003. 파츠는 생성 시 IScanCycle에 자기 Scan을 등록하고, 외부에서 직접 호출하지 않는다

상태: 승인됨
날짜: 2026-09-27


## 배경

ADR 0002로 동작 완료와 타임아웃 같은 시간 기반 판단을 장치의 주기 메서드 한 곳에서 하기로 했다.
C#에는 PLC 런타임처럼 매 사이클 FB를 불러주는 주체가 없으므로, 누가 이 메서드를 주기적으로 부를지 정해야 했다.
조건은 세 가지였다.
모듈 없이 파츠 하나만 선언해도 감시가 동작해야 한다(Q3의 Manual 단독 조작 근거와 같은 이유).
테스트에서 실제로 기다리지 않고 시간을 재현할 수 있어야 한다(사양서 6.5).
실행 구조와 테스트 구조가 같아야 한다. 테스트에서만 외부가 직접 호출하는 구조는 배제한다.


## 선택지

### 안 1: 테스트와 상위가 Update를 직접 호출

Update를 public으로 두고 테스트는 직접, 실행 시에는 파츠마다 자기 타이머 루프를 둔다.
장점: 추가로 만들 것이 없다.
단점: 테스트 구조와 실행 구조가 다르다. 실행 시 파츠마다 타이머가 따로 돌아 Update끼리 서로 다른 스레드에서 동시에 실행될 수 있다.

### 안 2: 파츠가 주입받은 스캔 사이클에 자신을 등록

Core에 IScanCycle(Register(Action scan))을 두고, 파츠는 생성자에서 자기 Scan을 등록한다.
스캔 사이클이 주기마다 등록된 Scan을 등록 순서대로 호출한다.
장점: 파츠가 스스로 등록하므로 단독 선언으로도 감시가 동작한다. Scan을 private으로 숨길 수 있다. 모든 Scan이 루프 하나에서 순서대로 실행되어 Scan 간 동시 접근이 없다(PLC 태스크 하나 안의 FB 호출 순서와 같다).
단점: 인터페이스 하나와 실행용·테스트용 구현이 필요하다.


## 결정

안 2를 택한다.
메서드 이름은 Update 대신 Scan으로 한다. 외부 호출이 없고, PLC 한 스캔 동안의 처리라는 의미가 드러나며, Register(Action scan)과 짝이 맞는다.
Register는 생성자의 마지막에서 호출한다. 실행용 스캔 사이클은 다른 스레드에서 계속 돌기 때문에 조립이 끝나기 전에 Scan이 불리면 안 된다.


## 결과

테스트는 FakeScanCycle(FakeClock, 주기)을 쓴다. RunScans(duration)가 시계를 한 주기씩 밀며 등록된 Scan을 호출하므로 실제 대기 없이 수 초 분량을 재현한다. 테스트 코드에 Scan 호출이 등장하지 않는다.
실행용 스캔 사이클(PeriodicTimer 루프, SystemClock)은 실제 장치 구현체를 만드는 5주차에 Infrastructure에 작성한다.
실행 순서는 등록 순서다. 파츠가 모듈보다 먼저 생성되므로 파츠 Scan → 모듈 Scan 순서가 된다.
남는 문제: UI나 시퀀스에서 들어오는 명령 스레드와 Scan 스레드 사이의 동시 접근은 이 결정으로 해결되지 않는다. 실행용 스캔 사이클을 만들 때 다룬다.
남는 문제: 스캔 기반 모듈의 Scan(void) 안에서 Task<bool> 명령을 호출하는 방법이 정해지지 않았다. Load Lock 구현 전에 결정한다. → ADR 0004에서 해소(명령 메서드를 동기 bool로 변경).
