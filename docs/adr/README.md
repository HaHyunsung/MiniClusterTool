# 설계 결정 기록 (ADR)

ADR은 Architecture Decision Record의 약자다.
왜 이렇게 만들었는지를 결정 시점에 남기는 짧은 문서다.

이 프로젝트에서 ADR은 부수적인 문서가 아니라 핵심 산출물이다.
코드는 무엇을 했는지 보여주지만 왜 그렇게 했는지는 보여주지 못한다.
이직 면접에서 실제로 읽히는 것은 후자다.


## 작성 규칙

- 한 결정당 한 파일. 파일명은 NNNN-짧은-제목.md 형식.
- 번호는 0001부터 순서대로. 한 번 부여한 번호는 재사용하지 않는다.
- 결정이 뒤집히면 기존 파일을 수정하지 않는다. 상태를 폐기됨으로 바꾸고 새 ADR을 쓴 뒤 서로 링크한다.
- 길이는 한 페이지를 넘기지 않는다. 길어지면 결정이 두 개 이상 섞인 것이다.
- 결정한 직후에 쓴다. 나중에 몰아 쓰면 당시의 고민이 사라지고 결과만 남는다.


## 목표 주제 (최소 8개)

- 통신 프로토콜 형식과 프레이밍 방식
- ORM 선택 (EF Core 대 Dapper)
- 실패 표현 방식 (예외 대 Result 타입)
- 상태머신 구현 방식
- 레시피 버전 관리 스키마
- UI 상태 갱신 전략
- 장치 인터페이스의 명령과 대기 분리 여부
- 인터락 판단 책임의 위치

사양서 8절의 설계 질문들이 그대로 ADR 후보다.
