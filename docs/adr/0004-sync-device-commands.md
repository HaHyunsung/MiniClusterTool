# 0004. 장치 명령 메서드는 동기 bool로 즉시 반환하고, 비동기성은 구현체 내부가 담당한다

상태: 승인됨
날짜: 2026-10-03


## 배경

Q1에서 명령과 대기를 분리했다. 명령 메서드는 Permissive를 확인하고 명령을 내보낸 뒤 수용 여부(bool)만 즉시 반환한다.
전송 성공, 장비 응답, 동작 완료는 모두 이후 Scan에서 State/Error로 판단하고, 아무것도 오지 않으면 장치 타임아웃으로 잡는다(ADR 0002, 0003).
그런데 시그니처는 Task<bool> OpenAsync(CancellationToken)로 정해져 있었다.
당시 근거는 비전 좌표 계산처럼 호출 시 스레드를 점유하는 외부 DLL이 장치 구현에 등장할 경우에 대비해, 점유하는 구현과 점유하지 않는 구현을 같은 시그니처로 받자는 것이었다.
스캔 기반 모듈(Load Lock)을 설계하면서 이 근거가 현재 구조와 맞지 않음을 확인했다.


## 선택지

### 안 1: Task<bool> 유지

장점: 사양서 5.3 "모든 장치 동작은 비동기이고 CancellationToken을 받는다"와 문구상 일치한다.
단점: 점유하는 구현에서 Task는 DLL이 끝나야 완료되므로 bool이 수용 여부가 아니라 작업 결과가 되어 Q1의 의미가 깨진다. 호출자인 Scan(void)은 await할 수 없어 결국 호출부가 점유 문제를 떠안는다. 점유하지 않는 구현에서는 Task.FromResult만 반환하므로 Task가 하는 일이 없다. 시그니처만 보면 기다려야 하는 메서드로 오해된다(실제로 설계 논의에서 반복된 오해).

### 안 2: bool로 변경, 점유 작업은 구현체 내부에서 별도 스레드로 실행

명령 메서드는 bool Open()처럼 동기이며 절대 블로킹하지 않는다.
점유하는 외부 호출이 필요한 구현체는 명령을 받으면 그 호출을 Task.Run으로 띄우고 즉시 true를 반환한다. 완료 여부는 자기 Scan에서 Task의 IsCompleted/IsFaulted로 확인해 State/Error에 반영한다.
TCP 구현체는 명령을 송신 큐에 넣기만 하고 실제 송신은 통신 스레드가 한다.
장점: 시그니처와 의미(즉시 반환, 수용 여부)가 일치한다. 호출자는 구현이 점유하든 아니든 같은 방식으로 쓴다. 별도 스레드 처리가 구현체 안에 갇혀 인터페이스 통일성이 유지된다. 기다리는 것이 없으므로 CancellationToken도 필요 없다.
단점: 사양서 5.3 문구와 어긋난다. 점유 작업을 감싸는 책임을 구현자가 잊으면 Scan 스레드가 멈춘다(인터페이스로 강제할 수 없다).


## 결정

안 2를 택한다.
비동기성은 명령 메서드가 아니라 스캔 스레드, 통신 스레드, 점유 작업용 내부 Task가 담당한다. 사양서 5.3의 의도(호출자가 장치 동작 때문에 막히지 않는다)는 이 방식으로 충족된다.
인터페이스 계약: 명령 메서드는 즉시 반환하며 블로킹하지 않는다. 반환값은 명령 수용 여부다.
적용 대상: IValve(Open/Close), IPump(Run/Stop). 이후 히터, 로봇 등 명령을 가진 장치 인터페이스도 같은 규칙을 따른다.


## 결과

스캔 기반 모듈의 Scan(void)에서 명령을 그대로 호출할 수 있다. ADR 0003의 남는 문제 중 "Scan(void)에서 Task<bool> 명령 호출"은 이 결정으로 해소된다.
테스트에서 async/await가 사라져 테스트 코드가 단순해진다.
점유하는 구현체가 처음 등장하면 내부 Task의 예외 처리(IsFaulted → Error 래칭)와 진행 중 재명령 처리 규칙을 그 구현체에서 정한다.
재검토 조건: 호출자가 명령 완료를 직접 기다려야 하는 구조(스캔이 아닌 async 메서드 흐름)로 모듈 구동 방식을 바꾸게 되면 다시 본다.
