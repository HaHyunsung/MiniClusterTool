# 미니 클러스터 툴 제어 시스템 — 프로젝트 사양서

작성일: 2026-08-28
대상: 하현성
목적: FA 도메인 위에 검증 가능한 소프트웨어 설계를 얹은 결과물 확보
기간: 8~10주 (주당 8~12시간 기준)


## 1. 프로젝트 개요

가상 장비(시뮬레이터)와 상위 제어 소프트웨어를 별도 프로세스로 분리해 구현한다.
두 프로세스는 실제 장비와 동일하게 네트워크 프로토콜로만 통신한다.
실물 장비 없이 전 구간을 재현하고 검증하는 것이 이 프로젝트의 핵심 전제다.

대상 장비는 반도체 미니 클러스터 툴이다.
Load Lock 1기, Transfer Module 1기(반송 로봇 1축 세트), Process Chamber 2기로 구성한다.
웨이퍼 25매 카세트 1개를 투입해 각 웨이퍼를 지정된 레시피대로 처리하고 반환하는 것이 전체 시나리오다.

도메인을 이미 아는 영역으로 잡은 이유는 두 가지다.
도메인 학습에 시간을 뺏기지 않고 설계에만 집중할 수 있고,
완성 후 이직 면접에서 "내가 아는 장비를 내가 설계한 구조로 다시 만들었다"는 서사가 성립한다.


## 2. 이 프로젝트가 메우려는 갭

각 항목은 사양서의 특정 제약과 1:1로 연결되어 있다.
제약을 지키지 않으면 갭도 메워지지 않는다.

인터페이스 미사용 → 모든 외부 I/O를 인터페이스 뒤로 강제 (6.2)
테스트 부재 → 장비 없이 시퀀스 전 구간 검증 (6.5)
C# 5년 공백 → .NET 8, async/await, Channel, DI, nullable 강제 (6.3, 6.4)
계층 분리 경험 부재 → 프로젝트 참조 방향 단방향 강제 (4, 6.1)
DB 설계 경험 부재 → 스키마를 직접 설계 (5.6)
Git 협업 방식 부재 → 브랜치와 PR 운영 강제 (6.7)


## 3. 시스템 구성

프로세스는 두 개다.

VirtualEquipment (콘솔 애플리케이션)
장비 하드웨어를 모사한다. 밸브 개폐, 펌프 동작, 압력 변화, 히터 승온, 로봇 이동을 시간에 따라 시뮬레이션한다.
TCP 서버로 동작하며 상위 제어 SW의 명령을 받아 상태를 변화시키고 주기적으로 상태를 보고한다.
물리 모델은 정밀할 필요가 없다. 지연과 상태 전이만 사실적이면 된다.

HostController (WPF 애플리케이션)
상위 제어 SW다. 장비 상태를 표시하고, 레시피를 관리하고, 시퀀스를 실행하고, 알람과 이력을 남긴다.

두 프로세스는 반드시 TCP로만 통신한다.
공유 메모리, 직접 함수 호출, 공용 static 클래스를 통한 연결은 금지한다.
이 경계가 무너지면 프로젝트의 의미가 사라진다.


## 4. 솔루션 구조

프로젝트를 다음과 같이 나눈다.

MiniCluster.Core
도메인 모델, 인터페이스, 상태머신, 시퀀스 엔진.
NuGet 패키지는 로깅 추상화 정도만 허용한다.
WPF, 네트워크, DB 관련 어셈블리를 참조하면 안 된다.

MiniCluster.Infrastructure
Core가 정의한 인터페이스의 실제 구현.
TCP 클라이언트, DB 접근, 파일 입출력, 시스템 시계.

MiniCluster.App
ViewModel, DI 컨테이너 구성, 애플리케이션 서비스.

MiniCluster.Ui
WPF View, XAML, 컨버터, 스타일.
코드비하인드는 순수 UI 동작(애니메이션, 포커스)만 허용한다.

MiniCluster.Simulator
가상 장비 프로세스.

MiniCluster.Core.Tests
Core 대상 단위 테스트.

MiniCluster.Integration.Tests
시뮬레이터를 띄운 상태의 통합 테스트.

참조 방향은 Ui → App → Core, Infrastructure → Core 단방향이다.
Core는 아무것도 참조하지 않는다.
반대 방향 참조가 필요해 보이면 그건 대부분 인터페이스를 Core에 두지 않았다는 신호다.


## 5. 기능 요구사항

### 5.1 가상 장비

시뮬레이터가 모사해야 할 대상은 다음과 같다.

Load Lock
게이트 밸브 2개(대기측, 진공측), 진공 펌프 1개, 벤트 밸브 1개, 압력 센서 1개.
펌핑 시 압력이 시간에 따라 감소하고 벤트 시 상승한다. 지수 곡선 또는 선형 근사 중 택일.
카세트 슬롯 25개를 가지며 각 슬롯의 웨이퍼 유무를 보고한다.

Transfer Module
게이트 밸브 3개(Load Lock, Chamber1, Chamber2), 상시 진공.
반송 로봇 1대. 동작은 Pick, Place, Home. 각 동작은 목표 위치와 소요 시간을 가진다.
암(arm)의 웨이퍼 유무를 보고한다.

Process Chamber 2기
게이트 밸브 1개, 히터 1개, 압력 센서 1개, 가스 밸브 3개.
히터는 목표 온도까지 정해진 승온율로 접근한다.
공정은 "가스 밸브 조합 + 목표 온도 + 유지 시간"으로 단순화한다.

시뮬레이터는 다음 이상 상황을 인위적으로 발생시킬 수 있어야 한다.
운영자가 콘솔 명령이나 설정으로 트리거한다.

- 밸브 응답 없음 (명령을 받고도 상태가 바뀌지 않음)
- 압력 도달 실패 (목표 압력에 영원히 도달하지 않음)
- 로봇 동작 중 정지
- 웨이퍼 감지 센서 불일치 (있어야 할 곳에 없음)
- 통신 지연 및 순간 단절

이 기능은 선택이 아니라 필수다.
정상 시나리오만 도는 시뮬레이터는 학습 가치가 거의 없다.

### 5.2 통신 프로토콜

프로토콜은 직접 설계한다. 다음 조건만 충족하면 형식은 자유다.

- 길이 기반 프레이밍을 사용한다. 개행 구분은 금지한다. 부분 수신과 패킷 병합을 반드시 다뤄야 한다.
- 요청과 응답을 상관관계 ID로 매칭한다. 순차 대기 방식은 금지한다.
- 상위가 요청하지 않아도 장비가 보내는 비동기 이벤트(상태 변경, 알람)를 지원한다.
- 하트비트 또는 타임아웃으로 연결 이상을 감지하고 자동 재접속한다.

페이로드는 JSON을 권장한다. 바이너리로 하면 학습 포인트가 통신 자체로 쏠린다.

메시지 종류는 최소 다음을 포함한다.
Command(밸브 개폐, 펌프 기동, 로봇 이동, 히터 설정), CommandAck, StatusReport(주기), Event(알람/상태 전이), Heartbeat.

### 5.3 장비 추상화

Core는 물리 장치를 인터페이스로 표현한다.
구체 시그니처는 직접 설계한다. 다만 다음 원칙을 지킨다.

- 인터페이스는 통신 방식을 노출하지 않는다. "TCP", "패킷", "JSON" 같은 단어가 Core에 등장하면 실패다.
- 모든 장치 동작은 비동기이고 CancellationToken을 받는다.
- 완료를 기다리는 동작(밸브 열림 확인, 압력 도달)과 명령만 던지는 동작을 구분한다.
- 상태 조회는 폴링이 아니라 이벤트 또는 관찰 가능한 형태로 제공한다.

최소한 다음 추상화가 필요하다.
밸브, 펌프, 압력 센서, 히터, 반송 로봇, 카세트, 그리고 이들을 묶는 모듈 단위(LoadLock, TransferModule, ProcessChamber).

### 5.4 상태머신

Load Lock은 명시적 상태머신으로 구현한다.
상태는 최소 다음을 포함한다.
Unknown, AtAtmosphere, Pumping, AtVacuum, Venting, Error.

요구사항은 다음과 같다.

- 허용되지 않는 전이는 예외 또는 실패 결과로 거부한다. 조용히 무시하면 안 된다.
- 각 전이에 타임아웃이 있다. 초과 시 Error로 간다.
- 상태 전이 이력이 남는다.
- 상태머신은 실제 장치 없이 테스트 가능해야 한다.

Process Chamber도 동일한 방식으로 상태를 정의한다.

### 5.5 시퀀스 엔진

웨이퍼 1매 처리 시퀀스는 다음과 같다.

카세트에서 웨이퍼 확인 → Load Lock 벤트 → 대기측 밸브 열기 → (웨이퍼 투입은 시뮬레이션) → 밸브 닫기 → 펌핑 → 목표 압력 도달 → 진공측 밸브 열기 → 로봇 Pick → 밸브 닫기 → Chamber 밸브 열기 → 로봇 Place → 밸브 닫기 → 공정 실행 → 공정 완료 → 역순 반환

전체 시나리오는 25매를 순차 처리한다.
2개 챔버를 병렬로 활용하는 스케줄링은 8주차 이후 확장 과제로 둔다.

시퀀스 엔진 요구사항.

- 시퀀스는 데이터로 표현되고 엔진이 해석한다. 하드코딩된 긴 메서드 하나로 만들면 안 된다.
- 일시정지, 재개, 중단(Abort)을 지원한다. 중단 시 안전 상태로 복귀하는 절차가 정의되어야 한다.
- 각 스텝은 실패 사유를 구조화해서 반환한다. 예외 던지고 끝내는 방식은 금지한다.
- 스텝 실행 이력이 남는다. 언제 시작해 언제 끝났고 무엇이 실패했는지.
- 엔진은 가짜 장치 구현체만으로 완전히 테스트 가능해야 한다.

### 5.6 데이터 영속성

SQLite를 사용한다. 스키마는 직접 설계한다.
최소한 다음 개념을 저장해야 한다.

레시피
공정 조건의 집합. 버전 관리가 필요하다. 실행에 사용된 레시피는 나중에 변경되어도 당시 내용을 재현할 수 있어야 한다.
이 요구를 어떻게 스키마로 푸느냐가 이 항목의 핵심 학습 포인트다.

웨이퍼 처리 이력
어떤 웨이퍼가 언제 어떤 레시피로 어떤 챔버에서 처리되었고 결과가 무엇인지.

알람 이력
발생 시각, 해제 시각, 코드, 심각도, 발생 위치, 부가 정보.

이벤트 로그
상태 전이와 시퀀스 스텝 이력.

설계 시 다음을 결정하고 그 이유를 문서에 남긴다.
정규화 수준, 시계열 데이터의 인덱스 전략, 이력 테이블의 파티셔닝 또는 정리 정책, 레시피 버전 관리 방식.

ORM은 EF Core 또는 Dapper 중 선택한다.
어느 쪽이든 Core는 DB 존재를 몰라야 한다. 리포지토리 인터페이스만 Core에 둔다.

### 5.7 알람

알람은 코드 체계를 가진다. 심각도는 최소 Warning, Alarm, Fatal 3단계.
Fatal은 시퀀스를 즉시 중단시킨다.
알람은 발생과 해제가 쌍을 이룬다. 활성 알람 목록과 이력이 구분되어야 한다.

### 5.8 UI

WPF + MVVM으로 구현한다.

화면 구성은 최소 다음 4개다.

Overview
클러스터 전체 모식도. 각 모듈의 상태, 밸브 개폐, 압력, 온도, 웨이퍼 위치를 실시간 표시.
도형과 색상으로 표현한다. 이미지 리소스는 필요 없다.

Manual
개별 장치를 수동 조작하는 화면. 밸브 개별 개폐, 펌프 기동, 로봇 이동.
인터락에 걸리는 조작은 버튼이 비활성화되거나 거부 사유가 표시되어야 한다.

Recipe
레시피 목록, 편집, 저장. 유효성 검증 포함.

Log
알람 이력과 이벤트 로그 조회. 기간 필터, 심각도 필터.

MVVM 요구사항.

- View의 코드비하인드에 비즈니스 로직이 없어야 한다.
- ViewModel은 WPF 어셈블리에 의존하지 않는 것이 이상적이다. 최소한 View 타입을 참조하면 안 된다.
- ViewModel은 UI 없이 단위 테스트 가능해야 한다.
- 상태 업데이트가 초당 수십 회 들어와도 UI가 멈추지 않아야 한다. 갱신 주기 제어를 직접 설계한다.
- CommunityToolkit.Mvvm 사용을 허용한다. 다만 첫 화면 하나는 INotifyPropertyChanged와 ICommand를 직접 구현해보고 넘어간다.


## 6. 설계 제약

이 절이 사양서에서 가장 중요하다.
기능은 못 만들어도 되지만 이 제약은 지켜야 한다.

### 6.1 참조 방향
Core는 다른 프로젝트를 참조하지 않는다.
빌드 설정에서 강제할 수 없으므로 매주 1회 참조 그래프를 직접 확인한다.

### 6.2 인터페이스
장치, 통신, 시계, 파일, DB 등 모든 외부 세계와의 접점은 인터페이스 뒤에 둔다.
new 키워드로 인프라 객체를 직접 생성하는 코드가 Core에 있으면 안 된다.

### 6.3 비동기
Thread.Sleep을 사용하지 않는다. Task.Delay와 CancellationToken을 쓴다.
async void는 이벤트 핸들러를 제외하고 금지한다.
.Result와 .Wait()를 사용하지 않는다.
장기 실행 루프는 Task와 CancellationToken으로 관리하고 종료를 보장한다.
장치 이벤트를 상위로 전달할 때 lock 기반 공유 상태 대신 System.Threading.Channels를 우선 검토한다.

### 6.4 최신 문법
.NET 8을 사용한다.
Nullable reference types를 활성화하고 경고를 오류로 처리한다.
불변 데이터 모델에 record를 사용한다.
DI는 Microsoft.Extensions.DependencyInjection을 사용한다. 싱글턴 패턴을 직접 구현하지 않는다.
로깅은 Microsoft.Extensions.Logging 추상화를 사용한다.

### 6.5 테스트
Core 프로젝트의 라인 커버리지 60% 이상을 목표로 한다.
시퀀스 엔진과 상태머신은 80% 이상.
가짜 구현체는 손으로 만드는 것과 모킹 라이브러리(NSubstitute 권장) 양쪽을 다 경험한다.
시간에 의존하는 로직은 시계를 주입해 테스트에서 시간을 조작한다. 실제로 5초를 기다리는 테스트를 쓰면 안 된다.
5.1의 이상 상황 각각에 대응하는 테스트가 최소 1개씩 존재해야 한다.

### 6.6 예외와 결과
예상 가능한 실패(타임아웃, 인터락 거부, 통신 실패)는 예외가 아니라 결과 타입으로 표현한다.
예외는 프로그래머 실수와 복구 불가능한 상황에만 사용한다.
Result 타입을 직접 만들지 아니면 라이브러리를 쓸지 결정하고 이유를 남긴다.

### 6.7 Git
main 브랜치에 직접 커밋하지 않는다.
기능 단위로 feature 브랜치를 만들고 GitHub에 PR을 올린 뒤 스스로 머지한다.
PR 본문에 무엇을 왜 이렇게 만들었는지 3줄 이상 쓴다. 이게 코드리뷰 경험의 대체물이다.
커밋 메시지는 Conventional Commits 형식을 따른다.
PR 하나의 변경량은 400줄 이내를 목표로 한다. 넘으면 쪼갠다.

### 6.8 문서
docs 폴더에 결정 기록을 남긴다.
형식은 ADR(Architecture Decision Record)을 따른다. 한 결정당 한 파일, 배경과 선택지와 결정 이유와 결과.
최소 8개를 목표로 한다. 프로토콜 형식, ORM 선택, Result 타입, 상태머신 구현 방식, 레시피 버전 관리, UI 갱신 전략 등.


## 7. 단계별 로드맵

### 1주차 — 골격
솔루션 구조 생성, 프로젝트 참조 설정, DI 컨테이너 구성, 로깅 설정, Git 저장소와 브랜치 규칙 확립.
빈 WPF 창과 빈 콘솔 앱이 각각 뜨고 로그가 파일에 남으면 완료.
완료 기준: 참조 방향이 4절과 일치하고, PR 1개가 머지되어 있다.

### 2~3주차 — 도메인과 인터페이스
장치 인터페이스 설계, 도메인 모델 정의, Load Lock 상태머신 구현.
실제 통신은 아직 없다. 메모리상의 가짜 장치 구현체로 상태머신을 돌린다.
완료 기준: 통신 코드 한 줄 없이 Load Lock의 펌핑/벤팅 전 시나리오가 테스트로 검증된다.

여기가 이 프로젝트의 승부처다.
2주 동안 UI도 통신도 없이 인터페이스만 만지는 게 답답하겠지만, 이 순서를 뒤집으면 얻는 게 없다.

### 4주차 — 시뮬레이터
가상 장비 프로세스 구현. 물리 모델과 상태 시뮬레이션.
콘솔에서 직접 명령을 입력해 밸브를 열고 압력이 변하는 것을 확인할 수 있으면 완료.
이상 상황 주입 기능 포함.

### 5주차 — 통신
프로토콜 설계와 구현. 프레이밍, 상관관계 ID, 비동기 이벤트, 재접속.
Core의 장치 인터페이스에 대한 TCP 구현체 작성.
완료 기준: 2~3주차에 만든 상태머신이 코드 수정 없이 가짜 장치 대신 실제 시뮬레이터로 동작한다.
수정이 필요했다면 인터페이스 설계가 잘못된 것이다. 무엇이 잘못이었는지 ADR에 남긴다.

### 6~7주차 — 시퀀스 엔진
시퀀스 정의 구조, 실행 엔진, 일시정지/중단/복구, 실패 처리.
웨이퍼 1매 전체 시퀀스가 시뮬레이터 상에서 돈다.
이상 상황 주입 시 시퀀스가 안전하게 중단된다.

### 8~9주차 — UI와 영속성
WPF 4개 화면, DB 스키마 설계와 구현, 레시피 관리, 알람과 이력.
완료 기준: 레시피를 만들고 실행해서 25매를 처리하고 이력을 조회할 수 있다.

### 10주차 — 정리
커버리지 보강, 리팩터링, README 작성, ADR 정리, 데모 영상 녹화.
README에는 아키텍처 다이어그램과 설계 의도를 담는다. 이게 이직 시 실제로 읽히는 부분이다.


## 8. 스스로 답해야 할 설계 질문

막힐 때 AI에게 물어도 되지만, 아래 질문들은 답을 받기 전에 먼저 자기 생각을 글로 적고 물어야 한다.
답만 받아 적으면 이 프로젝트는 실패다.

1. 밸브 인터페이스는 "열어라"와 "열릴 때까지 기다려라"를 하나로 합쳐야 하나 나눠야 하나.
2. 압력 센서 값은 밀어주는(push) 게 맞나 당겨오는(pull) 게 맞나. 둘 다 필요하다면 인터페이스는 어떻게 생겨야 하나.
3. 인터락 판단 책임은 상위 제어 SW에 있나 가상 장비에 있나. 실제 장비라면 어디에 있어야 하나.
4. 시퀀스 중단 시 이미 열린 밸브를 닫는 책임은 누구에게 있나. 엔진인가 스텝인가 장치인가.
5. 통신이 끊겼을 때 진행 중이던 시퀀스는 어떻게 되어야 하나. 재접속 후 이어서 갈 수 있나.
6. 레시피가 변경되었는데 그 레시피로 처리된 과거 웨이퍼 이력이 있다. 스키마로 어떻게 푸나.
7. 상태 업데이트가 초당 50회 들어온다. UI를 초당 50회 갱신하지 않으면서 정보를 잃지 않으려면.
8. Core의 상태머신이 시뮬레이터의 상태와 어긋났다. 누구를 믿어야 하나. 어떻게 복구하나.


## 9. 완료 판정 기준

다음을 전부 만족하면 완료로 본다.

- 시뮬레이터를 끄고도 Core 테스트가 전부 통과한다.
- 시뮬레이터를 켜면 25매 전체 시나리오가 사람 개입 없이 완주한다.
- 5.1의 이상 상황 5가지 각각에 대해 시스템이 안전하게 반응하고 알람이 남는다.
- Core 커버리지 60% 이상.
- ADR 8개 이상.
- PR 15개 이상, main 직접 커밋 0개.
- README만 읽고 처음 보는 사람이 아키텍처를 이해할 수 있다.


## 10. 하지 말아야 할 것

기능을 늘리지 않는다. 챔버를 4개로 늘리거나 SECS/GEM을 붙이거나 스케줄러를 고도화하려는 충동은 8주차까지 보류한다. 완주하지 못한 프로젝트는 가치가 0이다.

UI를 먼저 만들지 않는다. 화면이 먼저 생기면 로직이 화면에 붙는다. 지금까지 해온 방식이 그거였을 가능성이 높다.

AI에게 구조 설계를 통째로 맡기지 않는다. 이 프로젝트의 산출물은 코드가 아니라 판단 경험이다.
구현이 막히면 물어보되, "어떻게 설계해야 하나"를 묻기 전에 내 안을 먼저 만들고 그것에 대한 비평을 요청한다.

기존 회사 프레임워크를 참고하지 않는다. 참고하는 순간 그 구조의 한계를 그대로 복제한다.
