## 2. 확정된 설계 결정

다시 뒤집으려면 근거가 있어야 한다.

장치 명령
명령 메서드는 동기 bool로 즉시 반환하고 블로킹하지 않는다. bool = 명령 수용 여부. 완료/실패는 이후 Scan에서 State/Error로 보고, 아무것도 오지 않으면 장치 타임아웃.
OpenAsync가 응답을 기다린다는 전제로 다시 묻지 말 것(개발자가 여러 번 정정함).
점유하는 외부 호출(DLL 등)은 구현체 내부에서 Task.Run, 자기 Scan에서 완료 확인. TCP 구현체는 송신 큐에 넣기만 하고 통신 스레드가 송신(ADR 0004).

인터락: 장치가 명령별 Permissive로 판단. 장치 응답 타임아웃은 장치, 공정 타임아웃은 시퀀스/레시피.

시간 판단과 에러 (ADR 0002)
시간 기반 판단(동작 완료, 타임아웃)은 Scan 한 곳. 사건성 에러는 발생 지점에서 즉시.
에러는 장치가 래칭, Reset()으로 해제, 최초 원인 하나만 유지, 에러 중 명령 거부. 타임아웃 시 밸브 State는 Unknown. 에러 코드는 구현체별 enum.

스캔 구조 (ADR 0003)
IScanCycle.Register(Action). 파츠는 생성자 마지막 줄에서 자기 private Scan 등록. 외부 직접 호출 금지(테스트 포함).
스캔 스레드는 IScanCycle 구현체가 소유하고 등록 순서대로 호출(PLC 태스크와 동일). 객체가 각자 스레드를 돌리지 않는다.
여러 주기가 필요하면 IScanCycle 인스턴스를 늘린다(Fast/Normal). 직접 읽고 쓰는 객체는 같은 사이클에 둔다. 사이클·스레드 경계는 Channel(통신→스캔) 또는 스냅샷(스캔→UI)으로만 넘긴다.
통신, UI, 로그는 원래 별도 스레드. Auto는 별도 스레드가 아니라 모듈 Running 시퀀스가 스캔마다 진행.
테스트: FakeScanCycle(FakeClock, 10ms).RunScans(duration). 실행용(PeriodicTimer + SystemClock + lock)은 Infrastructure에 아직 없음.

OnDelayTimer(Core): TON 대응. Tick/Stop/ElapsedTime(시작 전·정지 후 0). 파츠는 clock을 타이머에 넘기기만 하고 필드로 들지 않는다. 예외: OperationStateMachine은 이력 시각용으로 clock을 필드로 든다.

가짜 장치: 초기 상태 생성자 주입, 같은 방향 재명령은 true만 반환(타이머 재시작 안 함), 이상 상황은 가변 멤버(RespondsToCommand). PumpState: Unknown/Starting/Running/Stopping/Stopped.

공통 추상화: IDevice 같은 한 덩어리 부모는 만들지 않는다. 히터·로봇·카세트는 밸브/펌프와 모양이 달라 공통부가 Name/Error/ErrorID/Reset 정도뿐. 하위 장치 계약은 기능별 인터페이스(ErrorReset → StandStill → Abortable)로 층 2에서 만든다.
IDevice 단일화와 GUI 버튼 자동 생성은 8주차까지 보류(개발자 동의, 번복 시 상기시킬 것).

계층과 상태 (2026-10-03)
디바이스 → 모듈 → 장비 3단. 각 계층은 바로 아래만 제어. 유닛 역할은 필요하지만 객체화는 필요할 때.
모듈 명령도 즉시 bool, 완료는 상태로(예: LoadLock Mapping).
상태 3구분: 운전 상태(Core) / 챔버 상태(진공 여부, 펌핑·벤팅. LL·TM·PM 공통) / 모듈 고유 상태(LoadLock 미매핑·매핑 완료·공정 중·배출 대기 등, 명칭 미정). 챔버·모듈 고유 상태는 Cluster.
상태머신은 운전 상태 하나. 진공 상태는 챔버 속성이고 Run 시퀀스가 조건으로 확인만 한다. 사양서 5.4의 요구(불허 전이 거부, 전이 타임아웃, 이력, 장치 없는 테스트)는 운전 상태 머신에 적용.
각 챔버는 단독 운전 가능해야 한다(LL 에러로 정상 PM이 멈추면 안 됨).
상위 웨이퍼 흐름 지시자는 두지 않는 방향, 모듈 간 직접 핸드셰이크. 웨이퍼 데이터 소유권 문제는 6~7주차(시퀀스)에 다시 본다.

운전 상태 모델 (ADR 0005, 구현 완료)
PackML 축약(TcHit FB_StateMachine과 같은 상태 집합·수락 규칙). 상태: None, Aborting, Aborted, Homing, Homed, Idle, Running, Pausing, Paused, Stopping, Stopped, SemiAuto. 모드: None, Manual, Maint, Auto.
두 층: 층 1 OperationStateMachine(상태·명령 수락·자동 전이·이력·타임아웃, 장치/시퀀스 모름) / 층 2 모듈 베이스(시퀀스 구동, 완료 조건 등록, 하위 에러 합산, 명령 전파) — 층 2는 미구현.
수락 규칙: Abort 항상(Aborting 중 재호출은 true만), Home=Aborted+Maint/Auto+NOT Error+HomePermissive, Run=Homed/Stopped/Paused+Auto+NOT Error+RunPermissive → Idle(Paused에서면 Resumed=true), Pause/Stop=Running/Idle+Auto, SemiAuto=Homed+Maint+NOT Error+SemiAutoPermissive(탈출은 Abort뿐). 거부 시 false, 상태·이력 불변.
상태 전이는 상태머신이 Scan에서 스스로 한다. 외부는 명령 6개와 Reset만. 완료 조건 Permissive 5개(AbortedCondition, HomedCondition, PausedCondition, StoppedCondition, RunningCondition). 층 2가 생성자에서 람다로 등록. 빈 조건 = 즉시 충족.
Trigger: 명령명 / Complete(전이 상태 완료) / Activity(RunningCondition에 의한 Idle⇄Running).
타임아웃 책임: Aborting은 상태머신 필수 / Homing·Pausing은 하위 장치 타임아웃이 주인, 상태머신은 선택 백업 / Stopping은 공정·레시피 타임아웃, 상태머신은 보통 null. TransitionTimeouts(TimeSpan Aborting, TimeSpan? Homing=null, Pausing=null, Stopping=null).
타임아웃 시 상태는 그대로, 에러만 래칭. 에러 대응(Abort)은 층 2. 자동 전이는 에러와 무관하게 진행, 에러는 새 명령 거부로만 작동(2026-10-04 개발자 결정).
Reset: 에러 해제, 전이 상태면 타이머 재시작.
모드: ModeSelector를 참조 공유(챔버별/공통은 조립 시 결정). 변경 규칙은 프레임워크 고정 — Manual: 전원 Aborted/Aborting, Maint·Auto: 전원 Aborted/Homed, None: 거부, 같은 모드: true. 장비는 모드별 Permissive(ManualPermissive/MaintPermissive/AutoPermissive)로 더 엄격하게만. 상태머신 생성자가 mode.Attach(this)(internal). 층 2에서 "하위 전원 StandStill"을 고정 규칙에 추가할 것.
명령 스레드와 Scan 스레드 동시 접근: 스캔 사이클이 가진 lock 하나로 직렬화(실행용 스캔 사이클 작성 시).

모듈 베이스 (구현 가이드 02 개정판, 2026-10-09 AI 결정, 구현 전. TcHit 직역 초판은 폐기)
에러: bool Error + int ErrorID → Fault? Fault (sealed record Fault(string Source, Enum Code, string Message)). null = 정상, 최초 원인 유지(??=), 해제는 ClearFault(). 에러 enum 이름은 XxxFault(ValveFault, PumpFault, AnalogSensorFault, OperationFault), None 멤버 없음. 발생 시각은 넣지 않음(알람 계층이 찍음).
기능 인터페이스는 서로 독립: IFaultSource(Fault, ClearFault — Name 없음: 이름은 장치 신원이지 고장 속성이 아님, 출처는 Fault.Source. Name은 장치 인터페이스가 각자 가짐) / IStandStill(StandStill) / IAbortable(bool Abort). IValve·IPump: IFaultSource, IStandStill / IAnalogSensor·OperationStateMachine: IFaultSource / ModuleBase: 셋 다. 모듈 등록 타입 IFaultSource, 기능은 OfType/is로 고름.
장치 StandStill = 진행 중인 명령 동작 없음. 에러 뒤 Unknown도 StandStill(Aborting 데드락 방지).
시퀀스: seqNo CASE와 Exec/Busy/Done 폐기. C# 이터레이터(IEnumerable<Step>, yield return). Step = record(Name, Func<bool>? Action, Func<bool>? Until, TimeSpan? Timeout). Step.Timeout이 공정 타임아웃 자리. SequenceFault{ActionRejected, StepTimeout}.
SequenceRunner(owner, clock): Start/Cancel/Fault? Advance(bool hold), Current, IsActive, IsCompleted, AtBoundary. 한 스캔에 스텝 하나(완료한 스캔에 다음 스텝을 꺼내지 않음). 실패한 스텝은 끝난 것으로 치고 Fault 반환, 다음 행동은 모듈이 정함. async/await는 스캔 스레드 밖에서 재개되므로 쓰지 않음.
ModuleBase: 상태머신을 protected 필드로 보유(상속 안 함), 실행기 3개(aborting/homing/running). abstract IEnumerable<Step> Aborting()/Homing()/Running(). 시퀀스는 명령 수락 시 Start(스캔에서 상태 보고 시작하지 않음 — 지난 IsCompleted가 남아 층 1이 바로 넘기는 문제 방지). Abort: 재진입 아니면 Homing/Running Cancel, Aborting Start, 하위 IAbortable 전파. Run: Paused 재개면 이어감, 아니면 새로 Start. SemiAuto: Start.
베이스 등록 조건: Aborted(abortingRunner.IsCompleted), Homed(homingRunner.IsCompleted), Paused(runningRunner.AtBoundary), Stopped(runningRunner.IsCompleted) — 넷 다 하위 전원 StandStill AND. Home/Run/SemiAutoPermissive: Fault is null. 파생은 RunningCondition과 추가 수락 조건만 등록.
Scan: ① Fault ??= 상태머신 Fault ?? 하위 첫 Fault ② 상태별 Advance(Pausing/Paused는 hold) — 결과를 변수로 먼저 받음(??= 오른쪽은 왼쪽 null일 때만 실행되므로) ③ Fault ??= failure ④ Fault이고 Homing/Idle/Running/Pausing/Stopping/SemiAuto면 자동 Abort(베이스 고정). Aborting 중 스텝 실패는 Fault만 남기고 다음 스텝 계속.
Running 시퀀스는 while(!StopRequested) 반복 구조. Stop(사이클 스톱)은 사이클을 마치고 메서드가 끝나면 Stopped. 대기 스텝 Until에 || StopRequested.
모듈 StandStill = 상태 Aborted/Homed/Paused/Stopped AND 하위 전원 StandStill. ModeSelector.AttachStandStill(internal): Maint/Auto 변경에만 적용, Manual 제외.
생성자 순서: 베이스 Register(Scan) 뒤에 파생 생성자 본문이 실행됨 → 실행용 스캔 사이클은 조립 완료 후 Start()(Infrastructure 요구 사항).
사양서 6~7주차 "시퀀스를 데이터로"는 스크립트 언어가 아니라 순서·분기는 C# 코드, 스텝 이름·타임아웃은 데이터로 해석. 정의 구조·실행·일시정지/재개/중단·구조화된 실패가 이번에 앞당겨짐.
뺀 것: 스텝 실행 이력, SemiAuto 1스텝 진행(hold로 구현 가능), 장비 계층, 알람 계층, 경고 등급.

   완료 조건 등록(시퀀스 완료 + 하위 전원 상태), 하위 에러 합산(Error = 자기 OR 하위), Abort/ErrorReset 하위 전파, 에러 시 Abort,
   ModeSelector 고정 규칙에 하위 StandStill 추가.
3. 챔버(진공 속성, 펌핑/벤팅) — Cluster.Domain.
4. LoadLock 모듈과 펌핑/벤팅 테스트(밸브 무응답, 압력 도달 실패 포함). 이게 통과하면 사양서 2~3주차 완료.
5. 실행용 스캔 사이클(Infrastructure, PeriodicTimer + lock) → 시뮬레이터 → 통신.

## 7. 새로 합류하는 AI에게

docs/02_AI_협업_지침.md를 먼저 읽는다. 특히 2-1절(구현 가이드 방식).

협업 방식 (2026-10-03~04 확정)
- 구현 단계마다 AI가 구현 가이드를 HTML 아티팩트로 만든다: 결정된 것, 만들 파일, 클래스 모습(멤버·시그니처·#region), 쓰인 C# 개념과 PLC/TwinCAT 대응, 대표 메서드 1개 본문 예시, 나머지는 할 일을 글로, 테스트 목록. md가 아니라 HTML로, 바로 열 수 있게.
- 개발자는 아티팩트 댓글로 질문한다. 댓글 스레드에 답하고, 필요하면 가이드를 고쳐 재게시한다.
- 메서드 본문은 개발자가 쓴다. 반복 작업(테스트 작성 등)은 요청하면 AI가 쓰고 03 문서에 기록한다.
- 설계 판단이 필요하면 AI가 답을 제시한다. 개발자 의견에 휩쓸리지 말고 C# 프레임워크로서 옳지 않으면 그렇다고 말한다. 다만 개발자가 현장 경험으로 반박하면(예: 전이별 타임아웃 성격, 에러와 전이 독립, 모드별 Permissive) 대부분 개발자가 맞았다. 근거로 판단한다.
- AI가 쓴 문서(사양서 포함)의 의도를 개발자에게 묻지 않는다. 사양서는 AI가 썼다.
- TcHit(참고 코드)은 참고만 한다(2026-10-09 개발자 지시). 목표는 TwinCAT 변환이 아니라 C#에서 쓰기 좋은 프레임워크다. TcHit 구조를 쓸 때는 C# 대안과 비교해 나은 이유가 있을 때만 쓰고, PLC 제약에서 나온 관습(int 에러 코드, 스텝 번호 CASE, 고정 배열, 선형 인터페이스 상속 등)은 C# 방식으로 바꾼다. ADR 0005의 "TcHit 기능별 인터페이스를 옮긴다"도 이 기준으로 다시 본다.
- 이미 정한 것을 다시 묻지 않는다(특히 장치 명령이 응답을 기다린다는 전제).
- 전체 그림, 위치를 정확히("어느 파일의 어느 메서드"), TwinCAT 비유로 설명한다. 한 답변에 논점을 여러 개 올리지 않는다.

보고서
- 주간 보고서는 docx, 4주차 양식(제목/조원/주제, 번호 절, 표, 그림·코드 캡처 자리 표시). 작업 로그 형태(결정과 한 일만, 느낀 점 없음). 저장: 코딩 학습/Claude outputs/주간 보고서, 파일명 "융합시스템심화종합설계_김하조_N주차 보고서.docx". 조원: 김주헌, 하현성.
- 보고서에 회사, TwinCAT 표준, TcHit, 참고 코드, ADR 언급 금지. 과제로서 새로 고민해 만든 것으로 쓴다. ADR은 내부 정리용이다.
- 기존 문서는 통째로 덮어쓰지 않는다(개발자가 캡처를 넣었을 수 있음). 수정 전 mtime 확인.

환경
- AI 작업 환경에는 dotnet이 없어 빌드·테스트를 못 돌린다. 코드는 읽고 추적해서 검증하고, 실행 확인은 개발자 VS 테스트 탐색기로 한다. 테스트 탐색기에서 "실패한 테스트만" 필터가 켜져 있으면 새 테스트가 Test Not Run으로 남는다.
