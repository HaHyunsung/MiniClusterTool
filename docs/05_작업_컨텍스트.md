## 2. 확정된 설계 결정

다시 뒤집으려면 근거가 있어야 한다.

명령과 대기를 분리한다 (Q1)
명령 메서드는 동기 bool(Open/Close, Run/Stop)로 즉시 반환하고 블로킹하지 않는다. bool은 명령 수용 여부다. 완료는 State로 본다.
점유하는 외부 호출(DLL 등)은 구현체 내부에서 Task.Run으로 돌리고 자기 Scan에서 완료를 확인한다. TCP는 송신 큐에 넣기만 한다(ADR 0004, 2026-10-03 Task<bool>에서 변경).

인터락은 장치가 Permissive로 판단한다 (Q3)
IValve, IPump 모두 명령별 Permissive를 가진다.

장치 응답 타임아웃은 장치가, 공정 타임아웃은 시퀀스/레시피가 갖는다.

시간 기반 판단은 Scan 한 곳에서만 한다 (Q9, ADR 0002)
동작 완료 전이와 타임아웃을 모두 Scan에서 판단한다. getter는 값만 반환한다.
이전의 "State를 읽을 때 시계로 계산" 결정은 대체되었다(전이와 타임아웃 판단 시점이 갈라져 State와 Error가 어긋나기 때문).
통신 실패처럼 발생 순간이 있는 에러는 발생 지점에서 즉시 세운다.

에러는 장치가 래칭하고 Reset()으로 해제한다. 최초 원인 하나만 유지한다 (Q10, Q11)
에러 중에는 명령을 거부(false)한다. 타임아웃 에러 시 State는 Unknown(실제 위치를 모르므로).
에러 코드표는 구현체마다 enum으로 둔다(ValveErrorCode, PumpErrorCode, AnalogSensorErrorCode). 구현체마다 에러 원인이 다르기 때문.

스캔 구조 (ADR 0003)
Core의 IScanCycle.Register(Action scan). 파츠는 생성자 마지막 줄에서 자기 private Scan을 등록한다.
외부에서 Scan/Update를 직접 호출하지 않는다. 테스트도 마찬가지다.
테스트: FakeScanCycle(FakeClock, 10ms).RunScans(duration)가 시계를 밀며 등록 순서대로 Scan 호출.
실행용 스캔 사이클(PeriodicTimer + SystemClock)은 5주차에 Infrastructure에 만든다.

OnDelayTimer (Core)
TON 대응. 생성자로 IClock을 받는다. Tick()=시작 시각 기록, Stop()=정지, ElapsedTime()=경과(시작 전·정지 후 0).
파츠는 필드로 타이머를 갖고 clock은 타이머에 넘기기만 한다. IClock/IScanCycle은 필드로 들고 있지 않는다(생성자에서만 사용).

가짜 장치 규칙
초기 상태를 생성자로 받는다. 같은 방향 명령이 동작 중에 다시 오면 true만 반환하고 타이머를 재시작하지 않는다(반복 명령으로 타임아웃이 밀리는 것 방지).
이상 상황은 가변 멤버로 주입한다(RespondsToCommand). FakeAnalogSensor의 Value는 클래스에서만 set 가능.
PumpState: Unknown, Starting, Running, Stopping, Stopped.
FakeAnalogSensor 에러 = 유효 범위 이탈(현재 Value 기준).

FakeValveTests는 스캔 배선 확인용으로 남겨 둔다. 가짜 장치 자체를 검증하는 테스트는 더 만들지 않는다. 진짜 검증 대상은 LoadLock.

폴더: Core 파일은 Devices, Timing, StateMachine 등 폴더로 나누되 네임스페이스는 FabStack.Core 하나로 통일한다(2026-10-03). 클래스 이름은 Operation 접두어 유지.

계층 (2026-10-03 개발자 결정)
디바이스 → 모듈 → 장비 3단. 유닛(디바이스 묶음)은 필요할 때 추가. 각 계층은 바로 아래 계층만 제어한다.
모듈 명령도 디바이스와 같은 규칙: 즉시 bool 반환, 완료는 상태로 따로 본다(예: LoadLock Mapping).
Mode와 State는 장비에 고정하지 않고 별도 객체로 만들어 가져다 쓴다. 모드를 가진 요소는 하나일 수도 여럿일 수도 있다(챔버별 모드 / 공통 모드).
범용 상태머신은 Core에 둔다.
상태는 세 층으로 나눈다 (2026-10-03 개발자 결정)
운전 상태: FB_StateMachine/PackML 대응(Abort/Home/Run/Pause/Stop). 거의 모든 장비에 필요하므로 Core.
챔버 상태: 진공 여부, 펌핑/벤팅 등. LoadLock 고유가 아니라 LL·TM·PM이 공통으로 갖는 챔버 요소의 상태.
상태머신은 운전 상태 하나뿐이다. 진공 상태는 상태머신이 아니라 챔버가 가진 속성이며, Run 시퀀스는 그것을 조건으로 확인만 한다. 둘을 엮지 않는다. 챔버 상태와 모듈 고유 상태는 Cluster 쪽.
사양서 5.4(LoadLock 상태 Unknown/AtAtmosphere/Pumping/AtVacuum/Venting/Error를 상태머신으로)는 이 결정과 다르다. 5.4의 요구(불허 전이 거부, 전이 타임아웃, 전이 이력)는 운전 상태 머신에 적용한다. ADR로 남길 것.
유닛 역할(디바이스 묶음 동작)은 필요하다. 별도 객체로 만들지는 당장 정하지 않는다.
모듈 고유 상태: LoadLock의 미매핑/매핑 완료/공정 중/배출 대기 등(명칭 미정).
상위 시퀀스(웨이퍼 흐름 지시자)는 두지 않는 방향. 모듈끼리 직접 핸드셰이크. 단 웨이퍼 데이터 소유권 문제(ALD Cluster에서 LL 리셋 시 웨이퍼 데이터 삭제, TM이 데이터 이동)는 6~7주차에 다시 본다.
Error/Abort는 지금은 장치별 멤버지만, 이후 TcHit처럼 상위→하위 Abort/ErrorReset 전파, 하위 Error 상위 취합 구조로 분리할 가능성이 크다.
참고 코드: 코딩 학습/참고 코드 (개발자가 만든 회사 TwinCAT 표준 HitTcMasterLib, ALD Cluster). 참고용이며 그대로 따르지 않는다. 사양서 10절의 "회사 프레임워크 참고 금지"는 개발자 본인이 설계한 표준이라 참고 허용으로 개발자가 결정.

IDevice 단일화와 GUI 버튼 자동 생성은 8주차까지 보류 (개발자 본인 동의, 번복 시 상기시킬 것).

   지금 공통 부모를 만들면 LoadLock이 그 위에서 돌고, 미루면 LoadLock을 빨리 본다. 개발자 선택.

- 범위 축소 순서: UI 4화면→2화면(Overview, Manual), DB는 레시피 버전+알람 이력, 이상 상황 5종→3종(밸브 무응답, 압력 도달 실패, 통신 단절), 커버리지·ADR 개수는 숫자에 매달리지 않음.

## 7. 새로 합류하는 AI에게

docs/02_AI_협업_지침.md를 먼저 읽는다.

이번 세션에서 확인된 것

- 개념을 조각으로 나눠 설명하면 이해가 안 된다고 명확히 말한다. 전체 그림, 실제로 돌아가는 예제를 선호한다. ScanSample처럼 이 프로젝트와 같은 구조의 다른 도메인 샘플이 효과가 컸다(설계를 대신하지 않으면서 구조를 보여줌).
- TwinCAT 비유(TON, FB 호출 구조, 스캔 사이클, VAR 선언)로 설명하면 빠르다.
- 한 답변에 여러 논점을 올리지 않는다. 지금 작업에 필요한 것만.
- "어느 클래스의 생성자", "어느 파일의 필드"처럼 위치를 정확히 말한다. 모호하면 바로 혼란이 생긴다.
- 선언과 생성(필드 선언 + 생성자에서 new) 같은 C# 기본 흐름도 빠뜨리지 말고 적는다.
- 설계 결정은 개발자가 한다. 선택지를 AskUserQuestion으로 주면 빠르게 고른다. 이미 정한 구조를 반복하는 작업(예: FakePump)은 요청 시 AI가 작성해도 된다. 대신 03 문서에 기록한다.
- 보고서는 작업 로그 형태(결정과 한 일만, 느낀 점 없음). 저장 위치는 코딩 학습/Claude outputs. 기존 문서는 통째로 덮어쓰지 않는다.
- 제 쪽 작업 환경에서는 NuGet이 막혀 xUnit을 직접 못 돌린다. 코드 검증은 대체 실행기로 하고, 최종 확인은 개발자 VS 테스트 탐색기로 한다.
- git 명령은 --no-optional-locks로 읽기만 한다(index.lock이 남아 VS 커밋을 막은 적이 있다).
